# 题库内容与裁判口径

三道题为本项目新写的虚构日常故事，没有复制第三方开源题库。这里记录公开元数据和维护规则；完整汤底、评分点、提示及测试预期仅放在服务端 `cloudfunctions/game/data/puzzles.js`。

| ID | 标题 | 难度 | 主要体验 |
|---|---|---|---|
| `parking-ticket` | 没看的电影 | 入门 | 从表面花钱追问到另一笔费用，练习因果比较 |
| `library-shout` | 图书馆里的大喊 | 普通 | 检查时间、场景和在场者身份，避免默认前提 |
| `shadow-photo` | 没有人的合照 | 普通 | 区分身体与可见轮廓，追问构图及人数对应 |

另有独立练习题「雨中的小周」，完整内容在 `cloudfunctions/game/data/tutorial.js`。它不进入正式选题目录；核心解释只有一条必要因果，不强制玩家重复题面已经明确的结果。练习同样维护 20 条提问和 4 条猜底预期。

## 每题必须维护的字段

- `surface` 只给玩家一个清晰谜面，不包含整个答案。
- `solution` 写完整且自洽的标准解释，不依赖现实商家政策或具体机构的真实行为。
- `facts` 写题内成立的事实。裁判依据题内事实，不从现实常识任意补故事。
- `requiredPoints` 写通关必需的因果要点，不把无关细节当作通关条件。
- `criticalContradictions` 写会推翻核心解释的错误陈述。
- `unspecifiedDetails` 列未设定细节，避免把“不知道”判成“否”。
- `irrelevantDetails` 单独列已知无关细节，避免与未设定信息混淆。
- `acceptableVariants` 用自然口语说明同义答案，但不以固定关键词决定通关。
- `hints` 固定三条，逐级缩小范围，玩家主动解锁。
- `testCases` 是人工预期，每题 20 条；`guessCases` 每题四类。新模型、新提示词或题目修订后重新回归。

## 判词顺序

1. 先按问句形式识别意图。单一明确命题即使未知也属于是非题；非是非题、问多件事、无法从上下文确定指代时先 `clarify`。
2. 题目已明确不影响核心解释的细节，返回 `irrelevant`，不暗示该细节真假。
3. 相关且能依据固定事实判定时返回 `yes` 或 `no`。
4. 相关但题目未设定、又无法可靠推导，返回 `unspecified`。

错误响应、输出不合规或内容拦截不属于以上判词。模型既有回答不能反过来修改标准事实。

## 猜底口径

只依据本次完整猜底陈述判断。核心要点与因果齐全且无矛盾时为 `solved`，方向成立但缺要点为 `incomplete`，关键错误为 `incorrect`，无法可靠判断为 `uncertain`。引用、否定或并列备选解释时，需要判断玩家实际主张。

针对新写故事，完全不同但表面也说得通的解释，不应靠“看起来合理”直接判通关。玩家应继续通过是非问题确认题内事实，再提交与这些事实一致的完整解释。若真实试玩证明标准题目存在两套同样成立的核心解释，应修题，而非责怪玩家。

## 不把题库发到前端

小程序只允许包含 ID、标题、难度和 teaser 的白名单元数据。不得把 `solution`、facts、评分点、未解锁提示或整份私有 JS 复制到 `miniprogram/`。结束后的汤底由服务端按局状态返回。

内容的许可字段用于记录本题来源与后续发布方式，不自动覆盖外部素材。仓库若引入其他代码、图片或录音，需独立核查许可并保留相应声明。完整题库的再发布权限以仓库所有者确定的许可为准。
